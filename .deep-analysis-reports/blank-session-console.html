Why new sessions open a blank console

6 September 2026 | DevTrees Windows desktop | Session-start regression

Executive summary

The managed-session launcher introduced in d860778 starts copilot --acp without CREATE_NO_WINDOW. Windows can therefore allocate a console for the child process. Its standard input and output are pipes, and standard error is discarded, so that console has nothing to display. The conversation is meant to appear inside DevTrees, not in this console.

An existing, uncommitted working-tree change already adds the missing flag. This investigation did not modify that change or rebuild/reinstall the application.

Findings

Missing Windows child-process creation flag

The managed-session path bypassed the existing hidden-process helper. Redirecting standard streams does not itself suppress console creation. This explains both the extra window and why it stays empty.

A source fix already exists, but is not in the older installed executable

The pre-existing local change defines a Windows-only helper using creation_flags(0x0800_0000) and calls it for the ACP process. It follows the established pattern in system.rs. Rebuilding and reinstalling is needed to deliver that change to the installed application.

One stale message still describes the old behavior

src\renderer\src\components\sessions\terminal-session-view.tsx:73

The resume toast says "in a new terminal" despite now using the managed-session route. This is misleading wording, not the source of the blank console.

Recommended correction

Keep the existing Windows-only CREATE_NO_WINDOW patch, rebuild the desktop application, and install/restart the updated executable. Preserve the ACP pipes: they carry the in-app session protocol. Do not restore the external-terminal route just to hide this regression.

Expected behavior after delivery: new and resumed sessions remain interactive inside DevTrees without an additional blank console window. An installed-app launch after rebuilding is still needed to establish the end-to-end outcome.
